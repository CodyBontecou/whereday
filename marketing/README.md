# Whereday marketing website

The production host is `https://whereday.com`. The static site lives in
`public/`; edits do not become public until deployment.

## Build and check

```sh
python3 marketing/scripts/build_site.py
```

This regenerates documentation from `scripts/build_docs.py`, renders articles and comparison
pages from `scripts/build_seo_pages.py` and `content/`, updates sitemap coverage,
and validates local links, fragment/ARIA targets, canonical URLs, H1 counts,
descriptions, JSON-LD, unresolved template tokens, and reachability of published
pages from the homepage through reader links. Canonical, schema, alternate,
404-only and nofollow links do not satisfy that navigation check. Python 3.9+ is sufficient;
no package installation is needed. A repeated build produces the same output.

The homepage, blog hub, and original private-journal article remain directly
editable HTML. The hub's `Blog.blogPost` list is synchronized from published
blog pages by `scripts/blog_inventory.py`; keep its visible guide links current.
The build checker rejects missing reader links or a stale structured article list.
Release-gated drafts and integration articles are not added to that blog list.
Keep generated HTML in version control. Change documentation in
its generator. Edit the newer articles and comparison in `content/`, with their
metadata in `scripts/build_seo_pages.py`, then rebuild. Do not patch only the
generated versions.

Apple's public US lookup confirmed **Whereday: Location History 1.8** on
October 30, 2026. The temporary iso.me store-listing notices have been removed.
Access copy distinguishes new-user plans from protected existing-user rights;
keep that distinction in both HTML and agent-readable Markdown. Historical
1.7.16 workflow checks retain their original dates and limits.

Content review dates are explicit. When materially updating a page, update its
visible date and structured data, plus the corresponding date entries in the
build scripts. Do not refresh every page's date to signal activity.

For checks without regeneration:

```sh
python3 marketing/scripts/check_site.py
```

The existing gated Cloudflare Web Analytics integration is retained. The shared
`public/assets/acquisition.js` adds coarse website counts after the same
exclusion gate allows collection. It also honors Global Privacy Control and Do
Not Track. It sends only an exact public page path, event, CTA placement, and

`POST /api/v1/acquisition` validates a maximum 512-byte same-origin JSON body
and updates `website_acquisition_daily` through the `SEO_DB` D1 binding. This
separate table shares the existing analytics database; it does not write app
onboarding records. Browser/gate failures lose events rather than delay a
navigation. The endpoint can receive synthetic or automated requests, so these
are coarse counters, not an audited attribution system.

Run the privacy/validation tests:

```sh

```

Initialize the local table and use the actual Pages runtime:

```sh
wrangler d1 migrations apply iso-me-onboarding-analytics --local --config marketing/wrangler.jsonc
cd marketing
wrangler pages dev public --port 8892
```

For an aggregate report covering 28 UTC calendar dates, including today's
incomplete counts:

```sh
python3 marketing/scripts/report_acquisition.py
```

For SEO review, compare two equal windows of completed UTC dates instead:

```sh
python3 marketing/scripts/report_acquisition.py --summary
python3 marketing/scripts/report_acquisition.py --summary --as-of 2026-10-26 --days 28
```

The cutoff is exclusive and defaults to today's UTC date. The second command
compares August 31–September 27 with September 28–October 25. It queries all
56 dates, excludes October 26, and reports page/source counts and absolute
changes. It never computes session conversion rates, percentage growth from
zero, or attributable installs. Days with recorded events do not prove
collector uptime; absent rows do not establish that no people visited.

Use `--input /path/to/wrangler-results.json` to replay a saved successful
Wrangler SELECT result without credentials or network access. The saved query
must cover both requested windows. The legacy raw report covers only 28 dates
including today, so it cannot establish coverage for a 56-date comparison.
Failures are errors, not empty successful reports. Verify the report with:

```sh
python3 -m unittest discover -s marketing/scripts -p 'test_report_acquisition.py' -v
```

Interpret `page_view` as page loads and `app_store_clicked` as activations,
not unique people, installs, or purchases. Referrer categories describe each
page's referrer: a later internal page does not retain the original search
source. Do not calculate an organic session conversion rate by joining these
rows. The UTC day is the server receipt day. The existing Search Console
baseline measures search-result clicks independently.

The helper runs `queries/acquisition.sql` in Wrangler query mode and prints its
JSON results. Do not use `d1 execute --file` to read this report: that path
returns import/execution statistics instead of the selected rows. Counts may
include verification or automated browser loads; they are not labelled as human
traffic by this collector.

Four pages now use Apple-generated campaign links: the homepage, private-journal
article, Google Timeline comparison, and GPX walkthrough. The genuine developer
provider token and stable campaign labels live in `content/acquisition.json`.
`campaign_links.py` rewrites download anchors during the build; public product
metadata and unmeasured pages keep their canonical App Store URLs. The homepage
QR encodes the same `seo-home` URL, checked against `assets/app-store-qr-url.txt`.
Regenerate the QR and its URL file when changing that configuration.

Apple campaign reports have thresholds and delays. Keep organic visits,
outbound activations, visible campaign downloads, and purchases separate.

After each deployment, record its date and inspect new URLs and sitemap
discovery in Search Console. Preserve the historical baseline and compare
explicit equal-length windows after allowing for reporting lag. A successful
HTTP response is not proof that Google indexed a page.

See [Apple's campaign-link documentation](https://developer.apple.com/help/app-store-connect-analytics/acquisition/campaign-links)

## Lighthouse

Run mobile and desktop Lighthouse audits for every page, sequentially so the
browser instances do not compete for CPU. Node.js/npm and Chrome are required.
Lighthouse is pinned to 13.5.0. The command exits nonzero if any category scores
below 100, and saves the full HTML/JSON reports plus `summary.json`:

```sh
python3 marketing/scripts/audit_lighthouse.py --output /tmp/isome-lighthouse
```

Use `--path / --path /docs/` to select pages, `--device mobile` or
`--device desktop` to select a device, and `--base-url http://127.0.0.1:8767`
to audit a local preview. The preview compresses text responses and supports Pages' clean legal URLs.
It does not reproduce edge routing, caching, or production-only analytics;
verify the deployed site separately. Scores depend on test conditions.

Responsive screenshot assets use 480px and 720px WebP variants alongside the
original 900px homepage images and 1206px article images. Keep `sizes` matched
to the rendered image width when changing layouts. Navigation icons include
1x and 3x WebP sources for high-density screens. The docs and SEO generators
inline their small shared stylesheets at build time to avoid a blocking request
on cold loads; keep editing `public/docs/docs.css` and `public/assets/seo.css`,
then rebuild.

## Agent-readable content

The build generates About/Contact pages, a branded `404.html`, Markdown copies
of all public content, and `public/_worker.js`. Edit response behavior in
`worker.js`, trust-page content and conversion in `scripts/build_agentic.py`,
and retrieval guidance in `public/llms.txt`, then rebuild.

The Pages Worker negotiates HTML/Markdown using `Accept`, sends `Vary: Accept`
and `Cache-Control: no-store` for content representations, and preserves static
assets. Unknown URLs return 404; Markdown requests get recovery links, and
requests to missing `/api/` paths receive JSON problem details. The site exposes only public product metadata at `/api/v1/product`, with its
OpenAPI contract at `/openapi.json`; it does not expose a hosted journal API.
Edit that payload and contract together in `scripts/product_contract.py`. The 404 template is excluded from the sitemap
and Lighthouse page sweep.

preview does not run the Worker):

## GPX browser tool and tutorial

The free viewer lives at `/tools/gpx-viewer/`, with a worked tutorial at
`/blog/check-gpx-file/` and a `/tools/` hub. Edit their source content and
`build_seo_pages.py`; the normal build includes them in navigation validation,
Markdown and the sitemap. `gpx-demo.mjs` is generated from the unchanged public
five-point synthetic export. Do not replace that evidence sample with personal data.

`assets/gpx-core.mjs` parses GPX 1.0/1.1 track points, routes and waypoints.
It preserves segment boundaries, diagnoses missing/invalid times and coordinates,
and exports a limited CSV point table. It is not full schema validation, file
repair or a restorable journal converter. Limits:10 MiB/50,000 source points;
plot sampling at2,000 points; preview at25 valid points. CSV includes all usable
coordinate points and guards untrusted text against spreadsheet formulas.

The tool excludes acquisition/Web Analytics scripts and the Worker adds a
Content Security Policy with `connect-src 'none'`, self-only scripts, no
referrers and `no-transform`. Protect slashless and direct-index aliases too.
No external map tiles, geocoding, file uploads or local-storage persistence are
used. Following a normal outbound link leaves this boundary. Other site pages
retain their existing gated analytics.

Run `npm ci --prefix marketing` then `npm test --prefix marketing` for GPX
and Worker tests; the XML DOM package is a development dependency only.
The normal Python site build has no new runtime dependency.
